# 風險追蹤清單

來源：`docs/technical-plan.md` §7（主要風險）與 §4（授權風險），加上執行中發現的風險。狀態依實際 repo 現況查證（最近一次查證：2026-10-01，對照 `git log`、工作樹、`python3 -m pytest -q` 56 passed）。專案整體進度見 `docs/status.md`。

| 風險 | 影響 | 對策（來自技術規劃） | 狀態（2026-10-01 查證） |
|---|---|---|---|
| 訓練資料與手機側拍落差大 | 公開資料多為轉播或實驗室畫面，模型在真實使用情境（手機側拍）準確率可能大幅下降 | 編列標註人力與預算，建立自有資料集 | **尚未處理**。沒有任何真實影片進入 repo；所有測試皆為合成素材。需使用者決定是否提供真實影片（`docs/status.md` §5(b)）。 |
| 標註成本 | 需標註擊球時間點、球位置、球場角點，人力成本高 | 先做半自動標註工具 | **部分緩解（僅工具）**。`labeling/label_shots.py` 半自動標註工具已存在且有測試，但**已標註 clip = 0**；只涵蓋擊球時間點，球位置與球場角點無工具；標註人力與預算未確認。工具未在真實影片上跑過。 |
| 單鏡頭球速精度有限 | 只能得到估計值，精度不及雷達，過度宣稱會有產品/信任風險 | 定位為估計值；產品文案避免宣稱精確測速 | **尚未處理**（M5 未開始）。目前 API/設計文件以 null →「尚未分析」處理，沒有宣稱球速；正式文案與誤差門檻未定。 |
| GPU 成本 | 球追蹤（TrackNet 等）需 GPU，批次處理成本隨影片量增加 | 批次排程、按影片長度計費 | **仍未處理（僅有設計層面）**。上傳佇列無 worker、無 GPU 排程、無計費；`mlops/` 僅有模型登記（未提交），無成本監控。沙盒無 GPU，成本從未實測。 |
| 現有開源網球專案成熟度不足 | 球場線偵測、球員偵測等開源範例多為研究原型，穩定性不足以直接上線 | 只當起點參考，不直接自行上線使用 | **尚未處理**（持續性風險）。球場四角檢查仍是 stub；球員選擇是「最大/最中央」stub；尚未引入任何開源球場/球員偵測。 |
| YOLOv8（AGPL-3.0）授權風險 | 若用於球員偵測，SaaS 商用可能被迫開源 Rally AI 自身程式碼 | 詳見 `docs/decisions/0001-player-detection-license.md` | **已決定**（2026-09-30 使用者裁示：接受 AGPL-3.0，Rally AI 開源）。決策已記錄；落實部分見下一列（LICENSE）。另：`cv/player_selection.py` docstring 仍寫「不要用 YOLOv8」，與 ADR 不一致（過時文字，待 cv-engineer 更正）。 |
| **LICENSE 檔案仍是 placeholder（新增）** | `LICENSE` 不是 AGPL-3.0 正式全文；在此狀態下公開發布，授權不具效力、與 ADR 0001 的決定不一致，並有授權聲明瑕疵 | 以 gnu.org 的 AGPL-3.0 正式文字**逐字**取代；README 授權聲明同步 | **未處理，發布阻擋項**。查證：`LICENSE` 內容為說明文字 + 「PLACEHOLDER」註記。須在任何公開發布前換成逐字全文（不可憑記憶重建），並請使用者/法務核對。同時，AGPL 公開 repo 與資料集隱私（真實影片中的人物）需分開處理。 |
| **從未有真實影片跑過 Rally AI pipeline（新增）** | 所有「通過」的測試只證明邏輯在合成訊號上正確；M1 全程追蹤、M2 擊球數準確度、機位穩定門檻的真實表現皆未知，可能在首批真實素材上大幅失準（尤其 M2 手腕速度偽陽性，與 M0 啟發式門檻） | 計畫 §6 的驗收標準本身要求真實比對；對策＝取得首批真實影片（`docs/status.md` §5(b) 提案）並端到端跑通 | **未處理**。56 個測試全為合成素材；無 worker，上傳後不會進入任何處理。QA 也只在合成影片上測過。 |
| 機位穩定檢查為啟發式（QA Finding 1，既有，補列） | 通過閘門的影片仍可能是移動鏡頭，下游球軌跡/homography 假設被破壞而不自知 | QA 建議累積位移 / 方向一致性 | **已修復，有已記載的殘餘限制**。慢速平滑平移現在會 FAIL（`tests/test_qa_boundary_cases.py` 已更新）；**方向反轉的平移仍可能漏過**，且新門檻為手選、未用標註影片校準。 |
| 擊球時間點只用手腕速度（新增） | 計畫 §3 要求「球軌跡突變 + 揮拍峰值」；目前缺球軌跡，非擊球的大幅手臂動作（發球拋球、split-step）會造成偽陽性，M2 擊球數可能系統性偏高 | 球追蹤到位後與球軌跡融合 | **未處理**（`ml/README.md` 已誠實記載）。偽陽性實際代價未知，須待標註資料。 |
| 驗收門檻未定義（新增） | M3「預設門檻」、M4「可接受範圍」、M5「誤差」都沒有數字，無法判定 done，也容易事後移動球門 | PM 提案數字、使用者確認 | **未處理**。已列入 `docs/status.md` §5(d)，需使用者確認產品定位後定案。 |
| M4–M5 時程風險（既有，§6 明文） | 球追蹤 + 球場校正 + 球速為最高技術風險，且依賴 GPU 與真實資料 | 預留較多時間 | **未處理**。M4–M5 皆 not started；排程需另加緩衝，且須在 M1–M3 真實驗證後才啟動。 |
