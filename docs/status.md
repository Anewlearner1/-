## 3. 真實 vs. stub 對照表

| 機位穩定檢查 | 真實但是啟發式 | `phaseCorrelate`；門檻手選、未校準；方向反轉的平移可漏過；穩定的手持/大型近景物件可騙過。 |

| 上傳佇列 / worker | **stub（無 worker）** | `passed=true` 會寫一筆 `queued` 的 SQLite 列（`backend/db.py`，**未提交**），**沒有任何東西消耗佇列，狀態永遠停在 `queued`**。無 GPU 排程、無計費。 |

## 4. 全域缺口（任何里程碑要「done」都繞不過）

1. **零真實資料**：無任何真實影片被標註；計畫 §7 第一風險（手機側拍落差）未被觸及。
2. **零真實影片跑過 pipeline**：M0–M2 的所有行為只在合成素材上測過。
3. **無球追蹤**：M2 的完整方法、M4、M5 全卡在這裡。
4. **無 GPU**：球追蹤（TrackNet）與 YOLOv8 的真實效能/成本皆無法在目前環境量測。
5. **多項驗收門檻是空白的**：M3「預設門檻」、M4「可接受範圍」、M5「誤差」都沒有數字；沒有數字就無法宣稱 done。

## 5. 需要使用者決定

以下只有專案負責人能決定；列出的是 PM 建議，**不是已做的決定**。

### (a) 發球 / 高壓球在 M3 是否納入 FH/BH 分類

- 背景：`docs/domain-standards.md` §3 指出發球與高壓球不是 FH/BH；計畫 F3 沒說是否排除。ml-engineer 目前正在做一個過渡性的「other」類別。
- 選項：(1) 排除，M3 只做底線抽擊（FH/BH），發球/高壓球標為「N/A」；(2) 納入為第三類（serve/overhead）；(3) 納入後再細分。
- PM 建議：**選 (1)+保留「other/N/A」類別**——範圍最小、與計畫 F3「Fore / Back 次數」文字一致、且不需要為發球另外蒐集標註。發球統計可列為 M3 之後的獨立項目。此建議的代價：發球為主的影片，M2 計得的擊球數裡會有一批沒有 FH/BH 標籤，儀表板文案需交代。
- 需要你決定後，我才會更新 M3 驗收標準與 ml-engineer 的範圍。

### (b) 是否提供真實影片；最小資料集提案

> 以下數字是**PM 的估計提案，不是技術規劃書的要求**，可依你的預算與可取得性調整。

目前的處境：沒有真實影片，M2/M3 的驗收標準（對人工標註比對、準確率門檻）在原理上就無法評估。建議最小可驗證資料集：

- **影片量**：約 15–20 支 clip，總計約 150–300 次擊球（M2 要有統計意義的最低量級；M3 若要看 FH/BH 的混淆矩陣，每類建議至少 ~50–100 拍）。
- **機位與環境多樣性**：至少 3 個不同場地/機位；底線後方高處腳架為主（符合 §5 規格），另含 2–3 支「刻意不合格」的素材（手持、低機位、平移）以校準 M0 品質門檻；至少包含日光與不同光線各一。
- **規格**：≥ 60 fps、純回合片段；含至少 2–3 位不同球員（含左手與單/雙手反拍各一）。
- **標註**：每支 clip 的**人工確認接觸幀**（用現有 `labeling/` 工具，由人逐一確認/修正）；其中一部分（建議 ≥ 5 支）請由**兩位標註者獨立標**以量測標註一致性。M3 另需每拍的 FH/BH 標籤。
- **球速（M5，可延後）**：若要做，需要少量有雷達或已知球速的素材；這項可以等 M3 完成後再決定。
- **使用者需決定**：是否提供（或授權取得）此類影片；影片中人物的隱私/同意與公開 repo（AGPL 開源）的資料處理方式（資料集不應直接進公開 repo）。

PM 建議：**優先提供這份資料集**——這是目前解鎖 M2/M3 驗證、也是唯一能把「partial」往 done 推進的路徑；沒有它，繼續寫更多程式碼只會增加「未驗證的程式碼」。

### (c) 借用 repo 的問題

- 事實：本專案目前位於 `Anewlearner1/-` 的 `rally-ai` 分支，因為 GitHub 整合無法建立新 repo。
- 風險：與無關專案混在同一 repo；公開發布（AGPL）時會連帶暴露不相干的歷史；分支名稱/權限/CI 都不獨立。
- PM 建議：**能建立時，由你建立一個專屬 repo**（建議在正式對外發布與首批真實資料進來之前），再把 `rally-ai` 分支歷史搬過去。這不阻擋目前開發，但應排在任何公開發布之前。

## 6. 建議的下一步順序（誰解鎖誰）

依計畫排序（M1–M3 先於 M4–M5；M4–M5 風險最高，須留緩衝）：

1. **【你】決定 (a)(b)(c)**；(b) 是整條路線的瓶頸。
2. **【PM】補上驗收數字提案**（M3 門檻、M2 比對容差，如 ±5 幀已在 ml/README 中建議）→ 你確認。無數字就無法驗收。
3. **【資料】取得首批真實影片 → 跑 `labeling/` 流程標註**（解鎖 M2 評估）。
4. **【ml-engineer】在首批標註上寫評估腳本，得出 M2 真實的擊球數誤差與偽陽性率**（目前完全未知）。這一步也同時回答「只靠手腕速度夠不夠用」。
5. **【cv-engineer】M1 在真實影片上驗證「全程穩定追蹤」**；再決定是否需要 YOLOv8 + ByteTrack（ADR 已放行）。這需要 GPU 才好量測效能。
6. **【ml-engineer】M3**：待 (a) 決定與 FH/BH 標註到位後，才開始訓練/評估。
7. **【backend】做出最小 worker**（讓 `queued` 能前進、`shots` 真的被寫入），端到端跑通一支真實影片——這會讓「真實影片跑過 pipeline」第一次發生，應在 M2 驗證前後盡早做。
8. **【mlops】取得 GPU 環境**並量測球追蹤/偵測實際成本——是 M4 啟動的前置。
9. **【cv】M4（球場校正 + 落點）→ M5（球速）**：技術風險最高，**排程須預留額外緩衝**，並且在 M1–M3 以真實資料驗證過之後才啟動；M4 同時能把 M0 的球場四角 stub 換成真實檢查。
10. **【frontend】M6 儀表板 + 同步**：設計已備；真實逐拍資料（至少 M2 的擊球時間點）到位後再實作，避免對著不存在的資料介面開發。
11. **【你/PM】發布前清單**：LICENSE 全文、專屬 repo、資料集隱私處理、產品文案不宣稱精確測速。
