# ADR 0001: 球員偵測模型的授權選擇（YOLOv8 / AGPL-3.0 問題）

- 狀態：**未決定，待使用者裁示**
- 相關章節：`docs/technical-plan.md` §3（模組與技術選型）、§4（授權風險）
- 影響範圍：M1 的「真正」球員偵測與追蹤（目前 M1 stub 僅為單人追蹤，不涉及此問題；但下一步若要做多球員場景的物件偵測，就會撞到本決策）

## 問題

`technical-plan.md` §3 建議球員偵測與追蹤採「物件偵測 + ByteTrack 類追蹤器」。目前業界最容易取得、文件最完整、效果最好的選擇是 **YOLOv8（Ultralytics）**。

但 YOLOv8 的授權是 **AGPL-3.0**，且 Ultralytics 對其解讀是：

- 如果 Rally AI 以 SaaS（網路服務）形式提供分析結果給使用者，即使沒有把程式碼給對方下載，AGPL-3.0 仍視為「對外提供服務」觸發了 copyleft 義務。
- 實務上這代表兩個選擇之一：**把 Rally AI 自己的程式碼也以 AGPL-3.0 開源**，或**向 Ultralytics 購買商業授權**（Enterprise License，依使用規模計費，需另外詢價）。
- 這不是工程實作細節，而是會決定「Rally AI 的原始碼將來能不能保持私有、能不能被投資人/客戶當作專有資產」的商業與法務決策，因此不應由工程 agent 自行決定，需要專案負責人（使用者）裁示。

## 選項

### (a) 購買 Ultralytics 商業授權
- 優點：可以直接用 YOLOv8 及其生態系（預訓練權重、Ultralytics 的工具鏈、社群資源最多、上線最快）；不必自己開源。
- 缺點：需要付費（金額依規模，需另外詢價，可能是持續性的授權費用）；等於把一項持續成本綁進產品的毛利結構；授權條款需法務審閱，確認涵蓋 SaaS 使用情境。
- 適合情境：Rally AI 確定要走閉源 SaaS / 商業產品路線，且預算允許。

### (b) 改用非 AGPL 的替代偵測器
- 具體選項例如：
  - YOLO 系列的非 AGPL fork 或更早版本（例如採用 GPL 之前的 YOLO 實作，或社群維護的 Apache/MIT 授權 fork ——需逐一查證授權條款是否真的乾淨，部分「fork」仍帶有上游 AGPL 殘留）。
  - 完全不同架構的偵測器，例如 Apache 2.0 授權的偵測模型（如部分 Detectron2 系列、或 MMDetection 下部分 Apache 授權的模型，需逐一確認，MMDetection 整體是 Apache 2.0 但個別模型權重來源可能另有授權）。
  - 自行訓練輕量偵測模型（成本最高，時程最長，但授權完全自主）。
- 優點：不受 AGPL 限制，程式碼可保持私有；避免持續授權費用。
- 缺點：效果、文件、社群支援通常不如 YOLOv8；需要額外的工程時間做模型評估、可能需要重新訓練或微調；存在「新技術不成熟」風險（呼應 §7 的開源專案成熟度風險）。

### (c) 接受 AGPL-3.0，將 Rally AI 開源
- 優點：不需額外付費，直接用 YOLOv8 生態系；若 Rally AI 的商業模式本來就偏向開源/社群路線，此選項反而是加分。
- 缺點：等於公開核心程式碼與可能的商業邏輯；若未來想轉為閉源或被併購，開源的既成事實難以逆轉；需要重新評估整體商業模式是否與開源相容。

## 尚未評估、需要先查證的事項
- 選項 (b) 列出的替代方案，其授權條款需逐一實際查證（本文件僅列出方向，尚未逐一確認每個 fork/模型的最新授權文字）。
- Ultralytics 商業授權的實際報價與條款細節（選項 a）尚未取得，需直接聯繫 Ultralytics 詢價。

## 需要使用者決定

以下決策只有專案負責人（使用者）能拍板，工程 agent（cv-engineer / mlops-engineer / product-manager）不會、也不應該自行選擇：

1. **Rally AI 的商業模式方向**：預計走閉源 SaaS，還是可以接受開源？這直接決定選項 (a)/(b) 還是 (c) 可行。
2. 若傾向閉源：**是否願意編列預算購買 Ultralytics 商業授權**（選項 a），還是希望改用替代方案以避免持續性授權費用（選項 b，但需額外工程時間）？
3. 這個決策會卡住 cv-engineer 接下來「真正」球員偵測/追蹤的開發（超出目前 M1 單人 stub 的範圍），需要在該項工作開始前定案。

在使用者做出裁示之前，建議 cv-engineer 的 M1 工作**維持目前單人 stub / 或使用 Apache 2.0 授權的元件**（如 MediaPipe、RTMPose，兩者依 §4 皆可商用），不要提前引入 YOLOv8 依賴，以免之後需要拔掉重做。
