# 儀表板設計（F1–F6）

> 設計對象：`frontend-engineer`（M6 交付：儀表板 UI + 影片同步）。
> 依據：`docs/technical-plan.md` §1 功能表、§6 M6 驗收標準（逐拍資料與播放進度一致）。
> 現況依據：`ml/README.md`（M2 現況）—— pipeline 今天只有 `ml/shot_timing.py::detect_shots()`
> 產出的 **contact frame / contact time / peak wrist speed**，**沒有** FH/BH 分類（M3 未做）、
> **沒有**球速估算（M5 未做）、也沒有落點/球場座標（M4 未做）。本設計刻意不假裝這些欄位已存在，
> 以免 frontend-engineer 對著一個目前後端給不出來的 API 介面實作。

## 0. 資料假設（寫給 frontend-engineer 的現況對照表）

| 儀表板元件 | 對應功能 | 今天 pipeline 是否有真實資料 | 沒有資料時顯示什麼 |
|---|---|---|---|
| 骨架疊圖 | F1 | 有（M1，`cv/pose_overlay.py`） | — |
| 擊球數 / 每拍卡片 | F2 | 有（M2，`ShotEvent.contact_frame/contact_time_s`） | — |
| FH/BH 標籤與次數 | F3 | **沒有**（M3 未做） | 「尚未分析」佔位，見 §3 |
| 每拍球速 | F4 | **沒有**（M5 未做；M2 只有 wrist speed，不是球速，單位/物理意義不同，不可借用顯示） | 「尚未分析」佔位，見 §3、§5 |
| 擊球時間軸 | F5 | 有（用 contact_time_s 排列） | — |
| 播放同步高亮 | F6 | 有（用 contact_time_s 對比 currentTime） | — |

frontend-engineer 串接時，`shot` 物件目前只能預期含：`contact_frame`、`contact_time_s`、
`peak_speed`（wrist speed，像素/幀或校正前單位，**不是球速**，不要顯示在球速欄位）、`wrist`
（left/right）。`fh_bh_label`、`ball_speed_kmh` 等欄位在 API 尚未提供前，前端應以「欄位缺席」
處理（optional/nullable），而不是預期永遠有值再补 0 或空字串。

## 1. 版面（Normal 狀態）

```
┌─────────────────────────────────────────────────────────┐
│  影片播放區（疊圖骨架，F1）                                  │
│  ┌───────────────────────────────────┐                   │
│  │                                   │  ▶ 00:42 / 03:10   │
│  │         (video + overlay)         │                    │
│  └───────────────────────────────────┘                   │
├─────────────────────────────────────────────────────────┤
│  擊球時間軸（F5）                                            │
│  ●──●──●──◉──●──●──○──○──○   （◉ = 目前拍, F6 高亮）         │
│  第1拍  第2拍 ...  第9拍                                     │
├───────────────┬─────────────────────────────────────────┤
│ 摘要卡（sticky）│  逐拍清單（可捲動）                            │
│ 擊球數: 9 (F2)  │  ┌─────────────────────────────────┐   │
│ 正拍: 尚未分析   │  │ 第4拍  00:14  尚未分析（FH/BH）    │ ← 目前拍高亮
│ 反拍: 尚未分析   │  │        球速：尚未分析              │   │
│                │  └─────────────────────────────────┘   │
│                │  ┌─────────────────────────────────┐   │
│                │  │ 第5拍  ...                        │   │
└───────────────┴─────────────────────────────────────────┘
```

- 左側摘要卡：擊球數 (F2) 永遠顯示實數；FH/BH 統計次數 (F3) 目前顯示「尚未分析」（非 0，
  避免被誤讀成「這場比賽 0 次正拍」）。
- 右側逐拍清單：每張卡片對應一個 `ShotEvent`。順序 = `contact_time_s` 遞增。
- 時間軸 (F5) 是清單的壓縮視覺化，非清單的替代品——手機窄螢幕可以先收合清單、只留時間軸。

## 2. 狀態：空 / 載入中

- **上傳後、尚未有處理結果**：整個逐拍區塊顯示骨架屏（skeleton loading），影片區可先播放原始
  上傳影片（若已可存取），標示「分析中，完成後會自動顯示擊球資料」。不要顯示假的 shot 卡片
  或 0 拍。
- **處理失敗 / quality gate 擋下**：不進入此畫面，導回 `upload-flow.md` 的重拍提示狀態。
- **處理完成但 0 拍偵測到**（例如整段影片被 M2 判定沒有擊球）：顯示明確空狀態文案「這段影片
  沒有偵測到擊球，可能是影片太短或球員動作不明顯」，並提供「重新上傳」連結，而不是空白清單。

## 3. FH/BH 標籤與球速：尚未存在時的呈現

兩者都用同一套視覺語彙，因為原因相同（M3、M5 都還沒做）：

- 文字：「尚未分析」（不用「無資料」「N/A」「--」，「尚未分析」明確傳達「未來會有，只是現在
  沒做」，對應 `docs/technical-plan.md` §6 的里程碑順序）。
- 視覺：灰階、斜體或降低不透明度的 pill/badge，和已有資料的欄位（例如擊球數字）明顯區分開，
  不用跟正常數值一樣的實心深色樣式，避免使用者以為那是一個真實的量測值。
- 不可用 0、空字串、或猜測值替代。0 次正拍和「沒分類」語意完全不同，混用會誤導使用者。
- Tooltip／info icon 可選配一句更長的說明（例如「正反拍分類功能開發中」），非必須但建議加，
  降低使用者困惑或客服工單。
- 一旦 M3／M5 API 欄位上線，前端只需把「尚未分析」判斷條件從「欄位不存在」改成「欄位仍為
  null」——設計上不需要改版面結構，只換掉 pill 內容跟樣式（灰階 → 實色）。

## 4. F5／F6：時間軸與播放同步的精確行為（M6 驗收標準）

驗收標準（§6）：「逐拍資料與播放進度一致」。具體規則：

1. **高亮判定**：目前高亮的拍 = 滿足 `shot.contact_time_s <= video.currentTime` 的最後一拍
   （也就是「最近一個已經發生的擊球」），而不是最接近 currentTime 的拍。播放到兩拍之間時，
   畫面應顯示「剛剛那一拍」的資料卡片，不是下一拍，也不是無高亮。
2. **播放前（currentTime < 第一拍時間）**：不高亮任何拍，時間軸、清單都維持未觸及樣式。
3. **更新時機**：跟著 `<video>` 的 `timeupdate` 事件節流更新（不需要逐幀），視覺切換要平滑
   （高亮區塊淡入/淡出，不要跳動），但邏輯判定本身用上述 1 的規則，不做時間內插估計。
4. **雙向同步**：
   - 影片播放 → 驅動時間軸/清單高亮（上述規則）。
   - 使用者點擊時間軸上的某一拍或清單卡片 → `video.currentTime = shot.contact_time_s`
     （可選擇往前留 0.5–1 秒緩衝，讓使用者看到擊球前的準備動作），並立即高亮該拍，不等下一次
     `timeupdate`。
5. **拖曳 seek bar**：拖曳中即時更新高亮（不要等放開滑鼠才更新），避免使用者覺得「卡」。
6. **清單自動捲動**：高亮拍變更時，逐拍清單自動捲動讓該卡片可見（但使用者手動捲動清單時，
   短暫（例如 3 秒無互動）內不要搶奪捲動位置，避免打斷使用者正在看的內容）。

## 5. 球速呈現：估計值的框架（避免看起來像雷達精度）

依 `docs/technical-plan.md` §3「球速計算方式」與 §7 風險表：單鏡頭只能得到估計值，精度不及
雷達測速，「產品文案需避免宣稱精確測速」。M5 尚未實作，以下是**未來**球速欄位上線時的呈現規範
（現在先用 §3 的「尚未分析」）：

- **用詞**：一律使用「估計球速」「約 XX km/h」，禁止單獨出現「球速：XX km/h」這種暗示精確測量
  的寫法。不用「radar」「精準測速」等字眼。
- **數值精度**：四捨五入到個位數或 5 的倍數（例如顯示 "約 85 km/h" 而非 "84.7 km/h"）——小數點
  本身就是一種暗示高精度的視覺訊號，要避免。
- **視覺樣式**：球速數字旁固定放一個小的「估計值」標籤／info icon，跟 FH/BH 標籤一樣用非純色
  的次要樣式（不要用跟擊球數一樣醒目的大數字樣式）。
- **長條圖（每拍球速，F4 的視覺化）**：Y 軸避免用精細的等分刻度暗示精度；可考慮用色帶區間
  （慢／中／快）取代連續精細數值軸，或至少在圖表標題／說明文字固定加註「估計值，僅供參考」。
- **首次出現處必有說明**：儀表板任何第一次出現球速數字的地方（摘要卡、逐拍卡片、圖表）都要有
  可見或一點即達的免責說明，內容對應 §3／§7 的限制原因（單鏡頭、非雷達），不要只在系統設定或
  FAQ 頁面才講。
- 當 M5 上線後仍建議保留「估計」字樣與此視覺分級，不應在真正有模型後就直接拿掉——因為方法論
  本身（腳位落點 homography 反推）永遠是估計值，不是雷達那種直接量測。
